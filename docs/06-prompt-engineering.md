# 06 · Prompt 工程：这个项目里的五类提示词

> 时间：2026-10-17
> 说明：不是"提示词技巧合集"，是这个项目里真实存在、真实改过的五类 prompt，以及它们为什么长这样。

---

## 一、全景

端侧 AI 应用里的 prompt 不是"一句话 system prompt"，而是分散在五个位置、各自承担不同职责的东西：

| # | 位置 | 作用 | 生命周期 |
|---|---|---|---|
| 1 | `PresetStore` 人格预设 | 决定回答风格与角色 | 跟随会话 |
| 2 | `ToolSpec` 工具 schema | 让模型输出可解析的 JSON | 跟随每一轮 |
| 3 | `RagEngine.buildPrompt` | 把检索结果组织成可引用的上下文 | 每次提问重建 |
| 4 | `skills/*.md` 技能 | 固定工作流的步骤与输出格式 | 关键词命中时 |
| 5 | `BenchmarkRunner` 测试 prompt | 性能基准，必须固定不变 | 永久固定 |

**这五类的约束完全不一样**：人格预设要短（占上下文）、工具 schema 要精确（决定可解析性）、RAG 模板要抗污染（决定可信度）、技能要具体（决定产出质量）、跑分 prompt 要稳定（决定可比性）。

把它们混在一起写一个"超级 system prompt"，是小模型上最典型的失败原因。

---

## 二、人格预设：说行为，不说形容词

`PresetStore` 里四个预设，每个都不超过 50 字。

```kotlin
Preset("translator", "翻译", "🌐",
    "你是翻译。只输出译文，不要解释、不要加引号、不要说明你在翻译。" +
    "中译英保持简洁自然，英译中保持通顺口语化。")
```

**为什么这么写**：小模型对"请帮我翻译"这种请求式指令反应很弱，会先解释一遍再翻译。而"只输出译文、不要解释"是**否定式行为约束**，模型更容易执行。

对比测试（1.5B）：

| 写法 | 实际输出 |
|---|---|
| "你是一个翻译助手" | "好的，我来帮你翻译这句话：……" |
| "只输出译文，不要解释" | 直接给译文 |

同理，"代码"预设写的是"优先给可直接运行的代码，少讲概念"，而不是"你是一个资深工程师"——后者只会让它自称资深工程师。

## 三、工具 schema：小模型的第一个坑

`ToolSpec.prompt` 里定义了三个工具，每个都带 JSON 示例。

```text
可用工具：
1. set_reminder —— 设置提醒
   {"tool":"set_reminder","args":{"content":"提醒内容","time":"yyyy-MM-dd HH:mm"}}
...
规则：
- time 必须是 24 小时制的 "yyyy-MM-dd HH:mm"
- 如果用户没有说清楚具体时间，不要调用 set_reminder，直接反问
```

### 实测：0.5B 会把 schema 当内容复述

问"你好"，0.5B 输出：

```
- 你只需要完成任务, 不要解释

示例: 设置提醒: 2021-03-27 07:56
2021-03-27 07:56

你好, 今天有什么安排? (需要回答)
```

**它把 schema 里的示例当成"待续写的内容"抄了出来。** 参数太少的模型分不清"示例"和"该输出的内容"。

### 处理方式：按档位关闭

```kotlin
val useTools = _state.value.recommendation !is Recommendation.Restricted
var system = if (useTools) preset.systemPrompt + "\n\n" + ToolSpec.prompt
             else preset.systemPrompt
```

极限档（0.5B）不注入工具 schema。代价是这台设备上不能调工具，收益是至少能正常回答——**这个取舍比"什么都能做但什么都做不好"强**。

### 另一条经验：缩短字段名

`"content"` / `"time"` 比 `"reminder_content"` / `"trigger_time"` 的解析成功率高。小模型生成长字段名时容易拼错字母。

## 四、RAG 模板：三个刻意的约束

```kotlin
appendLine("以下是用户设备里的资料片段：")
hits.forEach { hit ->
    appendLine("[${hit.rank}] 《${hit.chunk.docName}》$heading")
    appendLine(hit.chunk.text.trim())
}
appendLine("问题：$question")
append("""
回答要求：
1. 只依据上面列出的资料回答，不要使用资料以外的知识
2. 每个结论后面用 [编号] 标注来源，例如 [1]
3. 资料里没有的信息，直接回答「资料中没有提到」，不要推测
4. 用中文，简洁
""")
```

三个约束都不是随手写的：

**1. 用编号 `[1]` 而不是让模型复述文件名。**
小模型抄长文件名会错字（`LiteAgent技术方案.md` 被抄成 `LiteAgent技术方案. md`，中间多一个空格）。编号只有一位数字，几乎不会错。文件名映射由客户端做，不交给模型。

**2. 明确写"资料里没有就说没有"。**
不写这句，1.5B 会开始编。写了之后，它至少会说"资料中没有提到"。

**3. 只放 topK 段，宁可召回不全也不要膨胀上下文。**
手机上 prefill 是真实开销——这台设备 15 t/s，多塞 200 字就多等 13 秒。

### 一个反直觉的决定：检索没命中就不拼任何资料

```kotlin
if (hits.isEmpty()) return question
```

空结果时直接当普通对话处理，不拼"未找到相关资料"这种占位文本。

理由：拼了之后模型会开始"基于（不存在的）资料"胡说，而且白付一次 prefill。**宁可退化，不要假装在做 RAG。**

## 五、技能：把工作流写成 Markdown

`assets/skills/daily-briefing.md`：

```markdown
# 每日简报

## 什么时候用
用户说「今天要做什么」「帮我看看今天的安排」这类话时。

## 怎么做
1. 如果剪贴板里有内容，把它当作今天要处理的事项来源之一（不要念原文，提炼）。
2. 如果对话里提到过日程，一并算进去。
3. 信息不足时，**只输出你能确定的部分**，不要编造日程。

## 输出格式
今日重点
· （最多 3 条，按重要性排序）
```

**为什么用 Markdown 而不是代码里的字符串**：产品经理能改、能 review、能提交 PR。放代码里就只有程序员能动。

`SkillRouter` 只做两件事：关键词匹配、把文件内容拼进 system prompt。不引引擎、不做插件市场。

**第 3 条"信息不足时只输出能确定的部分"是必要的**：不写的话，0.5B 会编出一整天的日程。

---

## 六、跑分 prompt：必须永不改变

`BenchmarkRunner` 里三条固定 prompt（短 / 中 / 长），注释里写死了"换 prompt 等于换尺子"。

这是工程纪律，不是技术问题：**任何性能数据只有在测试条件不变时才有意义**。今天跑 8.3 t/s，明天改一个字跑出 9.1 t/s，那不是优化，是换题了。

---

## 七、在小模型上，这六条是硬经验

全部来自实测，不是推测：

1. **否定式约束比肯定式有效。** "不要解释" 优于 "简洁回答"。
2. **schema 越短越好。** 0.5B 会把长 schema 当内容复述。
3. **不要让模型做映射。** 编号给它，文件名客户端自己查。
4. **不给"资料"就别提"资料"。** 空结果时退化成普通对话。
5. **输出格式写死。** 给模板，不要给描述。
6. **加更多约束不等于更听话。** 试过给 RAG 加更长的分隔符、加"不要复述"指令，结果只是从"复述标题"变成"复述分隔符"。**约束的边际收益在某个点之后是负的。**

## 八、可复用的两个模板

### 模板 A：需要严格输出的场景

```text
只输出以下格式，不要任何其他文字：

<格式示例>

规则：
- <字段约束，写死格式>
- <什么时候不要输出，直接反问>
```

### 模板 B：基于给定材料的问答

```text
以下是用户设备里的资料片段：

[1] 《<文件名>》<标题路径>
<正文>

问题：<用户问题>

回答要求：
1. 只依据上面列出的资料回答
2. 每个结论后面用 [编号] 标注来源
3. 资料里没有的信息，直接回答「资料中没有提到」
```

两个模板都经过真机验证（0.5B / 1.5B 均可用）。

## 九、这份文档本身要说明的一件事

prompt 工程的产出不是"一段神级提示词"，是**一套可复现、可解释、可回滚的约束集合**。

上面每一条改动后面都有一个"为什么改"，以及"改完什么效果"。没有这两个东西的 prompt 调整，都是在碰运气。
