# ADR 0003 · 中文检索用字级 bigram，不引分词库

- 状态：已采纳
- 日期：2026-10-17

## 背景

本地文档检索需要 BM25。BM25 的前提是"词"，而中文没有空格，必须先切词。

三个选项：
- (a) jieba 类分词库 + BM25
- (b) 字级 bigram + BM25
- (c) embedding 模型 + 向量检索

## 决策

第一阶段用 **(b) 字级 bigram**。第二阶段再叠加 (c) 做混合检索。

## 理由

1. **零依赖**。"量化精度" → `量化 / 化精 / 精度`，不需要词典文件。jieba-analysis 的词典约 5MB，对 APK 是实打实的体积。
2. **天然抗 OOV**。"SM8550"、"甜气AI"、"RK3568" 这类专有名词，分词库很容易切错，bigram 不受影响——它们在索引里就是一串 2-gram。
3. **BM25 的召回对切词粒度不敏感**。BM25 只看 term 命中，bigram 的 term 更细粒度，召回通常不降反升。

## 代价

- **索引膨胀**：同样文本，bigram 的 term 数约为分词结果的 1.5-2 倍。500 个块量级下仍可接受。
- **精确性下降**：查询"机器学习"会命中"机器"和"学习"，可能召回只提到"学习"的无关段落。用 IDF 加权和 top-K 限制缓解。
- **纯英文查询会退化**：英文按词切（已有处理），中英混排时英文词和中文 bigram 混在一个倒排表里，IDF 尺度不同。

## 放弃的方案

**(a) jieba + BM25**：召回更精确，但要多 5MB 词典，且要为专有名词维护自定义词典。

**(c) 直接上向量检索**：语义召回最好，但要引 embedding 模型（bge-small 约 90MB）+ 向量存储，第一阶段成本太高。MNN 自带 `Embedding` 类，第二阶段可以直接用，不需要 ONNX Runtime。

## 后果

- 检索质量在"术语密集"的技术文档上不如分词，在"口语化/专有名词多"的笔记上更稳
- 留下了 `Retriever` 接口，第二阶段加向量实现时上层不用改

## 什么时候该重新考虑

如果 10 篇文档 / 500 块的验收场景里，问"我上次方案的量化精度是多少"召不回正确段落，就说明 bigram 不够用，需要引入分词或 embedding。这个验收标准写在 README 里。
