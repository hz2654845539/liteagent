# ADR 0005 · 装不下的设备直接拒绝，不做降级硬撑

- 状态：已采纳
- 日期：2026-10-17

## 背景

设备分级的自然延伸是"总能跑起来"：内存不足就用更小的模型，再不足就砍上下文。

按这个思路，2GB 设备应该推荐 0.5B + 1K 上下文。

## 决策

**内存低于 3.5GB 直接返回"不支持"，不推荐任何模型。**

## 理由

实测数据（公司一台 DNAKE v911 工控面板）：

```
SoC: Allwinner A537   GPU: Mali-G57   API: 35
totalMem: 1950 MB     availMem: 692 MB     Java 堆上限: 128 MB
```

0.5B 的 W4 权重约 400MB，加 KV cache 和 MNN 运行时，峰值轻松超过 900MB。这台机器可用内存只有 692MB——不是"慢"，是**根本放不下**。

硬推的结果是：加载到一半被 LMK 杀掉，用户看到闪退，且不知道为什么。

## 理由展开

1. **明确拒绝比随机崩溃体验好**。用户在设置页看到"这台设备内存不足，无法运行端侧模型"，比点了加载然后闪退强得多。
2. **崩溃会污染性能数据**。埋点上报里混入一堆 OOM 记录，反而看不出真实瓶颈。
3. **这本身是产品能力**。"能判断自己跑不动"比"努力跑然后死掉"更专业。

## 代价

- 少了一批极低端设备的用户（但那批设备本来也用不了）
- 需要在 UI 上做一个"不支持"状态，而不是只处理成功路径

## 实现

```kotlin
if (profile.totalMemMb in 1 until rules.unsupported.belowTotalMemMb) {
    return Recommendation.Unsupported(
        rules.unsupported.message.replace("X", formatGb(profile.totalMemMb))
    )
}
```

阈值 3500MB 放在规则文件里，可以热更新——如果将来 MNN 出了更省内存的方案，改 JSON 就能放开。

## 后果

- `Recommendation` 做成 sealed interface，`Unsupported` 是一等公民，不是异常路径
- 测试里有一个专门用例：`2GB 工控机判定为不支持`
- README 的设备分级表第一行就是"< 3.5 GB → 明确拒绝"

## 一个反例说明为什么值得

如果按"总能跑"的思路，2GB 设备会拿到 0.5B + 1K 上下文的推荐。用户下载 531MB、等 5 分钟、点加载、闪退、再试、再闪退——最后给一星差评，理由是"这破 App 一开就崩"。

明确拒绝只损失一次转化，硬撑损失的是口碑。
