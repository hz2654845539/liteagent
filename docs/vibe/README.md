# Vibe Coding 协作记录

这个目录记录本项目里 **5 个真实的 AI 协作案例**，全部来自实际开发过程，不是事后编的。

每个案例的结构一致：需求 → 我给的 prompt → AI 首版输出 → 出了什么问题 → 我怎么改 prompt → 最终方案 → 说明了什么。

## 从这 5 个案例里提炼的 5 条规则

**1. 让 AI 自证，而不是让它自信。**
每条结论标注【已核实·附路径】/【高置信推测】/【未确认】。案例 01 里它给出的路径是编的，但命名空间和方法名是对的——这种"七分真三分假"最危险，只有要求给行号才能戳穿。

**2. 验收标准必须能被机器判断。**
"编译成功"不是标准，"产物里有 59 个 `Llm::` 符号"才是。案例 02 花了 5 分钟编译，却因为少一个开关得到了一个空壳库。

**3. 不要问"这段代码对吗"，要问"哪个循环退出了"。**
案例 03 的代码静态审视挑不出毛病。真正的问题在行为层：用户点停止之后，到底哪一层知道了。

**4. 用真实数据跑边界，不要用自己编的数。**
案例 04 的规则表看起来毫无破绽。拿真机的 `totalMem` 一跑，两个档位全错。所以推荐引擎有 10 个用例，用的都是实测值。

**5. 记录失败比记录成功有用。**
成功案例只能证明"AI 能用"，失败案例才说明"我在哪里刹住了它"。这也是为什么这 5 篇里有 5 篇都是失败。

## 附录 · 效率对照：一天到底产出了什么

JD 里写"10 倍提升研发效率"。这个数字我没法证明，但可以把一天的产出摊开，让人自己判断。

### 可数的产出（约 10 小时）

| 类别 | 数量 |
|---|---|
| Kotlin | 4092 行 / 27 文件 |
| C++（JNI） | 328 行 |
| Python（后端） | 456 行 |
| 文档 | 24 篇 / 2714 行 |
| 单元测试 | 45（客户端）+ 14（后端） |
| 真机实验 | 线程扫描 4 组、1.5B 内存边界、RAG 端到端、release 包验证 |
| 修掉的坑 | R8 三个（serialization / 类名 / 回调名）、并发写、assets 路径、设备 FUSE、暂停符、UTF-8 切分 |

### AI 省掉了什么

- **查 API**：MNN 的 `Llm::response` 签名、`DiskEmbedding` 的存在，翻源码 3 分钟出结果，人肉读 CMake 要半小时
- **写样板**：Kotlin 数据类、JNI 的 NewStringUTF 模板、Compose 布局、FastAPI 的 Pydantic 模型
- **改编译错误**：`Mnn` vs `MNN`、`app` 不是属性、缺 import——都是秒级往返
- **文档骨架**：ADR 的格式、README 的结构、commit message 的措辞

### AI 没省掉什么

- **判断**：`DiskEmbedding` 能不能让 2GB 设备跑起 0.5B，这个判断错了两次才对
- **实测**：decode 到底是 3.7 还是 8.3 t/s，只能跑出来
- **环境**：MSYS 路径转换、FUSE 权限、systemui 卡死、输入法拿不到焦点——AI 看不到我的屏幕
- **架构决策**：为什么 RAG 比聊天重要、为什么拒绝低端机而不降级硬撑

### 诚实的结论

**代码量上，"10 倍"可能成立**；**交付质量上，不成立**——质量仍然来自人工验证。

今天最有价值的四个发现（R8 回调名、DiskEmbedding、mmap 让 1.5B 能跑、5 线程比 3 线程慢），**没有一个是 AI 主动告诉我的**。它们全部来自"跑一次看看"。

所以真正的提效公式不是"AI 写代码所以我快了 10 倍"，而是：

> AI 把"写"的成本压到接近零，于是"验证"成了唯一瓶颈。
> 谁的验证闭环快，谁才是真的快。

这也解释了为什么这个项目一半的时间花在真机上，而不是编辑器里。
