# 在 2GB 工控设备上跑端侧 LLM：可行性与降级方案

> 目标设备：DNAKE v911 / Allwinner A537 / 1950MB / Mali-G57 / Android 15 (API 35)
> 时间：2026-10-17
> 结论：**能跑，但只能做"短输出"任务。产品定位必须跟着改。**

---

## 一、先算账：为什么一开始判它"不支持"

设备实测值：

```
SoC: Allwinner A537（8×A55，实测 availableProcessors = 5，最高 1752 MHz）
totalMem: 1950 MB      availMem: 692 MB
Java 堆上限: 128 MB    可用存储: 22.9 GB
GPU: Mali-G57, GLES 3.2
```

最初看到 1950MB，直接归到"跑不了"——按 0.5B 权重 500MB + KV + workspace 估，怎么都要 700MB 往上，而可用只有 692MB。

这个判断错在哪？**把 531MB 全当成常驻内存了。**

## 二、重算：531MB 里有一半不进内存

`embeddings_bf16.bin` 是词表嵌入：151936 × 896 × 2 bytes ≈ 272MB，占了总量的一半。

但翻 MNN 源码 `transformers/llm/engine/src/llm.cpp:377`：

```cpp
mDiskEmbedding.reset(new DiskEmbedding(mConfig));
```

**无条件使用磁盘实现**。`DiskEmbedding` 通过 `seek_read` 按 token id 从文件里读对应行（`diskembedding.cpp:61`），不把整张表加载进内存。

为什么可以这样：一次生成的输入只有几十个 token，每个 token 读 896 × 2 = 1.8KB，几十 KB 的随机读，闪存毫无压力。

于是内存账变成：

| 项 | 大小 | 常驻 |
|---|---|---|
| `llm.mnn.weight`（W4） | 278 MB | 是 |
| `embeddings_bf16.bin` | 272 MB | **否** |
| KV cache @2048 | ~25 MB | 是（24 层 × 2 KV head × 64 dim × 2B × 2048） |
| MNN workspace | 50–150 MB | 是 |
| 进程其他 | ~50 MB | 是 |

**峰值 400–500MB**，可用 692MB —— 塞得下，但没有余量。

再加上 `use_mmap`（权重按页调页，不整块进 RSS），常驻可以压到 300MB 上下。

## 三、速度：能聊，但别指望长篇

A55 @1.75GHz 是低端核，decode 主要受内存带宽限制：

```
每个 token 要读一遍全部权重 ≈ 278MB
工控板 LPDDR4x 实际带宽估 8–10 GB/s
理论下限 ≈ 28–35 ms/token
乘以 A55 的实际效率（dequant + 计算开销）≈ 0.25–0.35
```

**估算 4–8 tok/s**（这是推算，不是实测）。

换算成体感：

| 场景 | 输出长度 | 耗时 | 能不能接受 |
|---|---|---|---|
| 工具调用（生成 JSON） | ~20 token | 3–5 s | ✅ 可以 |
| RAG 问答（一句话回答） | ~80 token | 10–20 s | ⚠️ 勉强，用户愿意等 |
| 闲聊（一段话） | ~250 token | 30–60 s | ❌ 不行 |

**这台设备上，"聊天机器人"是不成立的。"问答机 + 遥控器"是成立的。**

## 四、方案：三级降级，每一级都有用

### 第 1 级 · 极限模式（Extreme）

能跑，但参数全部压到最低：

| 参数 | 常规（8GB 机） | 极限（这台设备） |
|---|---|---|
| 模型 | 1.5B W4 | 0.5B W4 |
| 上下文 | 4096 | **1024** |
| 线程 | 6 | **3**（5 核留余量，避免内存争抢） |
| mmap | 内存紧张时开 | **强制开** |
| GPU | 有就开 | **关**（Mali-G57 的 OpenCL 驱动在 Allwinner 上不可靠，且 GPU 走统一内存反而抢 RAM） |

为什么线程只给 3：单线程带宽利用率低，但 4-5 线程会在 692MB 里互相抢 cache 和内存带宽，实测经常是"线程越多越慢"。3 是保守起点，要实测调。

**用户看到什么**：推荐卡片明确写"极限模式 · 0.5B · 1024 上下文 · 预计 4-8 tok/s"，让用户有预期，而不是点完骂慢。

### 第 2 级 · 仅检索模式（Retrieval-only）

模型加载失败或生成超时，**自动降到这一级**。

模型不跑了，但 RAG 检索还能用——BM25 是纯 CPU 字符串匹配，几 MB 内存，跟 LLM 完全无关。

用户问"方案里的量化精度是多少"，系统直接返回最相关的原文段落：

```
找到 2 段相关内容：

[1] 《方案.md · 技术选型》
推理框架选用 MNN，量化精度为 W4，模型体积约 500MB。

[2] 《方案.md · 备注》
量化精度还可以选择 W8，但显存和内存占用会翻倍。
```

**这比"设备不支持"好得多**：用户要的往往就是"我那句话写在哪个文件里"，这件事根本不需要模型。

### 第 3 级 · 明确拒绝

连检索都不行（没导入文档、内存 < 1.5GB、非 arm64），才回到现在的"不支持"。

## 五、产品定位的变化

这台设备上，产品从"通用助理"缩成两个具体场景：

**场景 A · 现场问答机**
工人拿着一台 2GB 面板，问"这个型号的参数是多少"，AI 从本地文档里翻出答案。不需要网络，不需要服务器，2GB 就够。

**场景 B · 语音/文本入口的遥控器**
说"提醒我下午三点巡检"，生成一个 20 token 的 JSON，3 秒完成。这比在 7 寸屏上点五层菜单快。

**不做**：长文写作、多轮闲聊、代码生成。

## 六、实现清单

| # | 改动 | 状态 |
|---|---|---|
| 1 | `rules/recommend-rules.json` 增加 `extreme` 档（1500–3500MB） | 待做 |
| 2 | `RecommendEngine` 支持极限档参数（1024 ctx / 3 线程 / 强制 mmap / 关 GPU） | 待做 |
| 3 | `LlmEngine` 加载失败时不再直接报错，返回一个可降级的错误类型 | 待做 |
| 4 | `RagEngine` 增加"仅检索"输出（不生成，直接拼原文） | 待做 |
| 5 | UI 增加"仅检索模式"的状态与开关 | 待做 |
| 6 | 用这台设备实测：能否加载、峰值内存、decode 速度 | **必须真机** |

## 七、必须实测才能定的三件事

1. **加载会不会 OOM**：估算 300–400MB，实际可能更高（MNN workspace 大小取决于模型图，我没法静态算准）。
2. **mmap 会不会拖垮速度**：首次 token 可能因为频繁缺页掉到 1-2 tok/s，热了之后恢复。如果一直热不起来，说明存储读带宽不够，得关掉 mmap 换常驻。
3. **3 线程是不是最优**：要试 2/3/4/5 四组。

这三件都是"跑一次就知道"的事，也是这台设备唯一能提供、我无法在 PC 上替代的信息。

## 八、实测结果（2026-10-17 17:02）

**结论：能跑。这是这个项目第一次真机出 token，而且是在一台 1950MB 的设备上。**

| 指标 | 实测值 |
|---|---|
| 模型加载 | 6.5 s / 7.6 s（两次） |
| decode | **3.7 → 8.3 tok/s**（对话 / 跑分） |
| Native Heap | 327 → 365 MB |
| TOTAL PSS | 432 → **486 MB** |
| TOTAL RSS | 546 → **596 MB** |
| 进程存活 | ✅ 未 OOM |

### 正式跑分（App 内「跑分」页，三条固定 prompt）

```
Qwen2.5-0.5B-Instruct-MNN
加载 6498 ms · 内存峰值 688 MB · 3 线程 · GPU 关

Prompt   输入   输出   首token   prefill   decode
短        1     64    230 ms   4.4 t/s   8.2 t/s
中        9    128    656 ms  13.8 t/s   8.5 t/s
长       20    256   1347 ms  15.1 t/s   8.3 t/s
```

三个数字值得单独说：

**1. decode 稳定在 8.3 t/s，不随输入长度变化。** 这符合预期——每 token 都要读一遍全部权重，成本固定。8.3 tok/s 意味着一个汉字约 120ms，人眼能跟得上，是可用的。

**2. prefill 从 4.4 爬到 15.1 t/s，短 prompt 那栏偏低是因为含首轮预热。** 15 t/s 折算下来：1000 字的文档要 67 秒才能 prefill 完。**这是 RAG 场景的真正瓶颈**——不是生成慢，是喂进去慢。所以这台设备上"仅检索模式"不只是兜底，很多时候是更优解。

**3. 内存峰值 688 MB，而可用内存是 692 MB。** 99%。

### 1.5B 也测了（这个结论推翻了我之前的判断）

我原本断定："内存就剩 4MB 余量，839MB 的 1.5B 必然 OOM。"

实测结果：

| 模型 | 加载 | 首 token | prefill | decode | VmRSS | 结果 |
|---|---|---|---|---|---|---|
| 0.5B | 6.5 s | 230 ms | 15.1 t/s | **8.3 t/s** | 495 MB | 推荐 |
| 1.5B | 13.3 s | 5789 ms | 5.3 t/s | **3.0 t/s** | 988 MB | 能跑，但慢 |

**它跑完了，没有 OOM。** 原因是两个我没算进去的东西：

1. **mmap**：829MB 权重不整块进 RSS，按页调入。实测 RSS 988MB 而不是 1.8GB。
2. **zram swap**：内核把一部分页压缩换出。切模型那次抓到的数据是 `TOTAL PSS 949MB / RSS 512MB / SWAP PSS 497MB`——近 500MB 被换出去了。

所以真正的边界不是"装不装得下"，而是"换页之后还能不能忍"。

答案是不能：

- **首 token 5.8 秒**：点发送后要愣 6 秒才出第一个字
- **3.0 tok/s**：一个汉字 330ms，比人手打字还慢
- **988MB RSS**：这台设备总共 1950MB，等于一半内存被一个 App 占着，随时可能被 LMK 带走

**结论修正**：极限档推荐 0.5B 依然正确，但理由要改——
不是"1.5B 装不下"，而是"1.5B 装得下但慢到不可用，而且内存余量归零"。

用户仍可手动切到 1.5B（现在允许），但那是他自己的选择，不是系统的推荐。

### 一个真实的权衡：快 vs 聪明

同样问"你好"，两个模型的输出质量差距很明显。

**0.5B**（8.3 t/s）：

> 好的，我是一个人工智能语言模型，可以回答各种问题。我被训练得非常出色……

一段话来回说，没有结构。

**1.5B**（3.0 t/s）：

> 作为AI助手，我不能直接评价一个应用程序的安全性。但是，我可以提供一些建议：
> 1. 从官方网站下载应用，避免从不明来源下载。
> 2. 确保应用没有被修改过，可以通过官方渠道下载应用。
> 3. 安装应用时，检查应用是否来自官方渠道……
>
> 以上建议可以帮助你选择和安装一个安全的应用程序，但请注意……

分点、有编号、有免责声明。这是 1.5B 相比 0.5B 最直观的提升——**不是更聪明，是更会组织**。

（答非所问是真的，问"你好"它在答"装应用安不安全"。但格式质量摆在那。）

所以这台设备上的真实选项是：

| 选 0.5B | 选 1.5B |
|---|---|
| 首 token 0.23s | 首 token 5.8s |
| 8.3 tok/s | 3.0 tok/s |
| 495 MB | 988 MB |
| 回答像复读机 | 回答有结构 |

**快但笨，或者慢但像样。** 这不是技术问题，是产品选择——默认给快的那个，把慢的那个留给愿意等的人。

### 我在这台设备上错了两次

| 判断 | 我的预估 | 实测 | 错因 |
|---|---|---|---|
| 2GB 跑不了 0.5B | 必炸 | 8.3 tok/s | 漏了 `DiskEmbedding`，272MB 词嵌入不进内存 |
| 2GB 跑不了 1.5B | 必炸 | 3.0 tok/s，988MB | 漏了 mmap 按页调入 + zram |

两次都是**低估了系统的内存管理能力**，把"文件大小"当成了"常驻内存"。

真实的边界比直觉宽 2.4 倍（0.5B → 1.5B），但"能跑"和"能用"之间的差距，比"能跑"和"不能跑"之间的差距更大。

对比预估：decode 估 4–8 tok/s，实测 3.7，略低于下限但同一量级。内存估 400–500MB，实测 PSS 486MB，吻合。

### 代价：系统被压到极限

加载期间 LMK 连杀了 7 个后台进程，包括 **`com.android.shell`**（adb 自己）：

```
lowmemorykiller: Kill 'com.android.dynsystem', oom_score_adj 985
lowmemorykiller: Kill 'com.android.federatedcompute.services', oom_score_adj 975
lowmemorykiller: Kill 'com.android.shell' (2074), uid 2000, oom_score_adj 955
lowmemorykiller: Kill 'com.softwinner.camera2', oom_score_adj 955
...
```

我们的进程因为在前台（`oom_score_adj` 较低）活下来了，但这说明 **596MB RSS 在这台设备上已经没有余量**。任何一次系统内存波动都可能把它带走。

### 输出质量：0.5B 的能力边界

生成是成功的，但内容是这样：

```
- 你只需要完成任务, 不要解释

示例: 设置提醒: 2021-03-27 07:56
...
你好, 今天有什么安排? (需要回答)
```

**它在复述 system prompt 里的工具示例，而不是回答 "hi"。**

原因不是链路有问题，是 0.5B 扛不住这段 prompt：里面既有工具 JSON schema，又有两条示例，还有"只输出 JSON"的强约束。参数太少的模型分不清"示例"和"该输出的内容"。

这直接推翻了一个设计假设：**小模型不能用复杂的工具 schema 做系统提示**。

修复方向（待做）：
- 极限档下**不注入工具 schema**（这种设备本来也不该指望它调工具）
- system prompt 压到 20 字以内
- 或者干脆走"仅检索模式"，把生成这一步省掉

### 顺带发现的两个真 bug

**1. 单步解码在第一个 token 后提前 break**

我们的循环用 `status == FINISHED` 判断结束，但 MNN 在 stepping 模式下**每个 token 之后都会把状态标成 FINISHED**。结果是生成 1 个 token 就退出，UI 上气泡是空的，但 perf 里有 decode 速度——非常迷惑。

修法：每步之后把状态 `const_cast` 回 `RUNNING`（MnnLlmChat 里叫 `restoreAndroidSteppingStatusIfNeeded`）。

**2. 规则文件路径少了一层**

Gradle 把 `rules/*.json` 复制到了 `assets/` 根，代码读的是 `assets/rules/`。因为 `runCatching` 吞掉异常，界面只显示"规则文件缺失"，没有任何日志。

修法：复制目标改成 `generated/assets/rules`。这个 bug 只有在真机上才暴露——本地测试和编译都不会报。

### 还没修的问题

`首 token 0 ms` 已修复：MNN 的 `ttfa_us` / `decode_us` 只在 `omni.cpp`（多模态路径）里赋值，纯文本路径只清零。现在由 JNI 自己计时，跑分页显示 230 / 656 / 1347 ms，随输入长度线性增长，合理。

`0.5B 复述 system prompt` 已修复：极限档不再注入工具 schema，输出从"复述示例"变成了正常中文回答。

**仍未解决：0.5B 不会自己停。** 它生成到 192 token 上限才停，中间会有明显的语句重复（"你好，很高兴认识你。你有什么问题或需要我帮忙吗？"循环三遍）。这是模型能力问题，不是 bug。缓解手段是把上限压到 192（约 2-3 句），但根治要靠 repetition penalty 或换更大的模型。
