# 05 · 线程数调优实验

> 设备：DNAKE v911（Allwinner A537，8 核但 `availableProcessors` = 5，最高 1752 MHz / 1950MB）
> 模型：Qwen2.5-0.5B-Instruct-MNN · W4 · 1K 上下文 · mmap · GPU 关
> 时间：2026-10-17 20:30
> 结论：**3 线程最优。5 线程比 3 线程慢 10%——线程不是越多越好。**

---

## 一、为什么做这个实验

`rules/recommend-rules.json` 里极限档写的是 `threads: 3`。这个 3 是拍的，理由是"5 核留余量"，没有任何实测依据。

而 JD 里明确写着"推理引擎的落地与**性能优化**"。没有实测的调优等于没调——所以补了这个实验。

## 二、方法

为了排除干扰，四组除了线程数其他全部固定：

| 项 | 值 |
|---|---|
| 模型 | 0.5B W4（同一份文件，page cache 已热） |
| 上下文 | 1024 |
| prompt | 跑分页的三条固定 prompt（短 1 tok / 中 9 tok / 长 20 tok） |
| 每组前 | `force-stop` 冷启动，重新加载模型 |
| 指标 | `decodeTps`（MNN 逐 token 计时，由 JNI 自采） |

用新加的两个自测参数驱动，不需要点 UI：

```bash
adb shell am start -n com.liteagent.app/com.liteagent.app.MainActivity \
  --es autobench "1" \
  --es automodel "Qwen2.5-0.5B-Instruct-MNN" \
  --ei threads 3
```

跑完自动把 JSON 写到 `files/benchmark/bench_<N>t_<ts>.json`，`adb pull` 出来汇总。

## 三、数据

**decode（tok/s），越高越好**

| 线程 | 短 prompt | 中 prompt | 长 prompt | 平均 |
|---|---|---|---|---|
| 2 | 8.38 | 8.34 | 8.27 | 8.33 |
| **3** | **9.69** | **9.66** | **9.48** | **9.61** |
| 4 | 9.12 | 9.23 | 8.95 | 9.10 |
| 5 | 8.30 | 8.87 | 8.75 | 8.64 |

**相对最优的差距**

```
3 线程  9.61  ████████████████████  基准
4 线程  9.10  ███████████████████    -5.3%
5 线程  8.64  ██████████████████     -10.1%
2 线程  8.33  █████████████████      -13.3%
```

每组内部三条 prompt 的 decode 非常接近（8.27~9.69），说明**decode 速度与输入长度无关**——符合预期，每 token 都要读一遍全部权重，成本固定。

**加载耗时**（附带数据，受 page cache 影响，仅供参考）

| 线程 | 加载 |
|---|---|
| 2 | 3477 ms |
| 3 | ~4000 ms |
| 4 | ~4500 ms |
| 5 | ~5000 ms |

**prefill 不可比**：四组在 4.0~25.0 tok/s 之间大幅波动，因为 page cache 状态和系统后台负载每次不同。要测 prefill 需要固定 cache 状态，这轮没做。

## 四、为什么 5 线程反而更慢

这台设备的 `availableProcessors` 是 5（8 核里有 3 个被系统或热插拔关了），主频 1.75GHz，LPDDR4x。

- **2 线程**：CPU 利用率不足，内存带宽没喂满
- **3 线程**：计算和带宽达到平衡点
- **4 线程**：开始出现 CPU 调度争抢，收益被抵消
- **5 线程**：占满全部可用核，系统没有余量做别的（渲染、GC、日志），反而拖慢

这和"核越多越快"的直觉相反，但在小模型 + 低端 SoC 上很常见：**decode 是内存带宽受限的，不是算力受限的**。加线程只会增加缓存争抢和调度开销，不会增加带宽。

0.5B 每 token 要读 278MB 权重，1.75GHz 的 A55 核根本跑不满内存，堆线程只会互相踩缓存行。

## 五、结论与改动

1. **规则里的 `threads: 3` 是对的**——但之前是运气，现在有数据了。
2. **不要按 `availableProcessors` 直接取线程数**。这台设备会取到 5，比最优值慢 10%。规则里固定 3 是更稳的做法。
3. 如果将来要支持更多机型，线程数应该由**实测**决定，而不是由核数推导。

## 六、这个实验暴露的两个问题

**1. `peakMemMb` 数据不可信**

四组的 `peakMemMb` 分别是 614 / 601 / 623 / 611 MB，差异只有 ±3%，但实际加载时间差 45%。说明这个字段不是真的"峰值"，可能是采样时机不对。

**2. prefill 无法横向对比**

page cache 状态不受控。要做得更严谨，需要每组前 `echo 3 > /proc/sys/vm/drop_caches`（需要 root），这轮没做。

## 七、复现

```bash
ADB=<你的 adb 路径> bash tools/thread_sweep.sh Qwen2.5-0.5B-Instruct-MNN "2 3 4 5"
```

脚本逐组冷启动 → 跑分 → 拉结果，最后直接打出对比表。一轮约 7 分钟。

前提：模型已在设备 `files/models/` 下，App 已安装。
