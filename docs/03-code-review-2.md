# 03 · 代码审查（第二轮）

> 时间：2026-10-17
> 范围：本轮新增的会话持久化、人格预设、工具扩展、导出、深色主题、R8 配置
> 说明：第一轮审查（`01-code-review.md`）针对的是核心链路，这轮针对产品化功能。

---

## P1-1 · 会话索引文件会被并发写坏

`SessionStore` 的 `save()` 是"读索引 → 改 → 写回"，而这个方法会在至少三个地方被调用：

- 生成结束（`persistSession()`）
- 切换会话（切走前保存当前）
- 删除会话

它们是不同的协程，没有互斥。两个 `save` 交错执行时，后写的会把先写的覆盖掉——表现为"某个会话从列表里消失"，或者索引里有条目但文件已被删。

**修复**：整个 `save` / `delete` / `list` 用同一把锁包住。会话数量在几十量级，全量互斥的代价可以忽略。

```kotlin
private val lock = Any()
fun save(session: Session) = synchronized(lock) { ... }
```

## P1-2 · 切换会话前不保存，会丢对话

```kotlin
fun switchSession(id: String) {
    sessionStore.load(id)   // 直接切走
}
```

如果用户刚发完一条消息、还没触发 `persistSession()`（比如生成被中断），切走之后这段对话就没了。

**修复**：切换前先把当前会话写回磁盘，再加载目标会话。

## P1-3 · 换人格不重置引擎，旧上下文会污染新人格

`setPreset()` 只改了 `presetId`，但 `LlmEngine` 的 KV cache 里还留着上一个人格产生的对话。

后果：切到"翻译"人格后，模型带着"我是资深 Android 工程师"的历史去翻译，输出会飘——可能先解释一遍再翻译。

**修复**：换人格时 `engine.reset()`。换人格等于换角色，历史不该带过去。

## P2-1 · 删除会话只有实现，没有入口

`deleteSession()` 写好了，UI 里却没有任何地方能调到。用户看得到一堆历史会话，删不掉。

**修复**：会话下拉菜单每项右侧加删除按钮。放在菜单项里而不是长按，是因为会话数量少，明确入口比隐藏手势安全。

## P2-2 · 剪贴板内容会被写进会话文件

`read_clipboard` 工具读到的内容会作为工具返回值回灌给模型，而模型的回复会连同工具结果一起进会话历史，落到 `files/sessions/*.json`。

这意味着：用户剪贴板里的密码、验证码、私聊内容，可能被永久存进本地文件。

**当前处理**：只截断到 800 字（防止吃光上下文），**没有做脱敏**。这是有意的取舍——端侧产品的隐私承诺是"不出设备"，不是"不落盘"。但这一点必须写进说明书，让用户知道。

**未来**：可以加一条规则，识别到疑似凭据（连续 16 位以上字母数字、`sk-` 前缀等）时不回灌，只在 UI 里显示。

## P2-3 · 后端每个请求都读一次 JSON

`load_rules()` / `load_catalog()` 每次调用都 `open()` + `json.load()`。规则文件只有几 KB，但这是完全不必要的 IO。

**修复**：`@lru_cache(maxsize=1)`。规则变更本来就伴随服务重启（它是部署产物），不是热更新配置。改了规则记得重启——这一点写进注释了。

## P2-4 · 死代码

`ToolRouter.stableId()` 没被任何地方调用（`ReminderTool` 自己算了 requestCode）。删掉，顺带清掉因此失效的 `java.util.UUID` import。

`SessionStore.delete()` 原来 `return true` 恒真，改成返回 `Unit`——一个永远为真的布尔值比没有返回值更有误导性。

## 这轮没修但记下来的

| 项 | 现状 | 为什么不修 |
|---|---|---|
| `exportCurrent()` 在主线程拼字符串 | 几千字的消息会卡几十毫秒 | 导出是低频操作，为它加协程+回调不值得 |
| 生成中长按可复制半截内容 | 会复制到不完整的句子 | 用户能看出来，且复制本身无副作用 |
| `SessionStore` 每次 save 都重写索引 | 会话多时是 O(n) 写 | n < 50 时无感 |
| 会话文件没有体积上限 | 单会话几千条消息时 JSON 会到 MB 级 | 端侧场景下极少出现，真出现再分页 |
| 后端 `/perf` 没有鉴权 | 任何人能写埋点 | 只监听 127.0.0.1，且是本地开发服务 |

## 二次审查的结论

第一轮的问题是"会不会崩"，这轮的问题是"会不会丢数据 / 会不会互相干扰"。

产品化阶段引入的多协程写同一份状态，是新的风险面——第一轮审查时只有一条生成链路，不存在并发写。**功能变多不等于复杂度线性增长，它带来了新的失败模式。**
