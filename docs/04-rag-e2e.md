## 一、怎么验的

RAG 的入口是系统文件选择器（SAF），在 adb 自动化里没法可靠操作。所以这次绕过 UI，直接把文档按存储格式写进应用私有目录：

```
/data/data/com.liteagent.app/files/documents/
├── index.json              → [{id, name, sizeBytes, importedAt, chunkCount}]
└── ragtest001/
    └── content.txt         → 正文化（已 normalize 换行）
```

写完之后 force-stop + 重启，`bootstrap()` 里的 `indexDocuments()` 会重新切块建索引。

**因此：SAF 选择器那一步没有被自动验证**，需要人工点一次（选文件 → 导入）。其余环节全部覆盖。

## 二、测试文档

一份 5 段的技术方案，埋了几个只有读文档才能答的事实：

## 技术选型      推理框架选用 MNN……

## 五、两个问题

### 1. 开头复述了一段 prompt 和资料标题

```
准确，尽量用句子回答，不要使用标点符号
LiteAgent技术方案
Qwen2.5-0.5B
```

模型把 system prompt 里的指令和检索片段的标题当成"待续写的内容"抄了出来。

这是 0.5B 的能力边界：它对"什么是指令、什么是资料、什么该输出"的边界感很弱。1.5B 以上不会有这个问题。

**不改 prompt 的理由**：试过加更强的分隔符和"不要复述"约束，只会换来另一种形式的跑偏。参数太少的模型，指令加得越多越容易抓错重点。

### 2. 答案里有 2/3 是资料原文而非提炼

它把三段检索结果几乎原样列出来了，只是加了引用编号。这其实是 **RAG 在弱模型上的一种合理退化**——既然模型不会总结，那就让它把原文摆出来，用户自己看。

这也反过来说明「仅检索模式」的价值：如果最终形态就是列原文，那不如省掉生成这一步，直接把 BM25 的 top-3 摆出来，快 20 倍。

## 六、性能含义

这台设备的 prefill 是 15 tok/s（见跑分）。三条检索结果拼进 prompt 大约 600 字 ≈ 400 token，**仅 prefill 就要 27 秒**。

所以在这台设备上：

- 短问答（资料短）→ 可用
- 长文档问答（资料长）→ 一分钟起步，用户很难等
- 仅检索模式 → 立刻出结果

**结论：极限档应该默认引导用户用"仅检索模式"做文档问答，把生成留给短问题。** 这条还没实现（当前是用户手动开关），但应该是默认策略。
